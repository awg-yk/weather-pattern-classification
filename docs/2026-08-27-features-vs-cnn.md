## オホーツク海高気圧(+0.122、2.0σ)。示唆的だが確定ではない

**これが計画の主題だった。**計画は次のように書いていた。

> オホーツク海高気圧は、記録が本当にオホーツク海高気圧の58枚に対してすら
> lift 1.24・peak的中率 8.6%。**正解のときですらオホーツク海を見ていない。**
> 物体検出で中心座標を明示的に取れば、位置は構造的に手に入る。

10ラベルのうち**唯一、特徴量がCNNを上回った。**しかもCNNが最も苦手として
いたラベルである。手がかりは `high_in_okhotsk_high`(AUC 0.883)で、全ラベル
全特徴量のなかで最も強い単独の信号だった。

**ただし確定と言うには足りない。**

- 差 +0.122 に対し、学習データを取り直したときの幅が ±0.053〜0.061。**2.0〜2.3σ**
- foldごとに 0.49 / 0.49 / **0.28** と割れており、**2025年のfoldは
  CNNの平均(0.299)を下回っている**
- 条件を変えた3回の実行で 0.499 / 0.453 / 0.421 と動く(差 +0.200 〜 +0.122)

**「位置を明示的に与えるとオホーツク海高気圧が良くなる」という方向は
支持されたが、大きさは確定していない。**再現するなら、この1ラベルに絞って
検出の精度を上げ、foldを増やして測り直すこと。

計画は「位置情報の欠如」という説明をCoordConvで試して否定していた
(F1 0.326→0.270)。CoordConvは座標を入力に足すだけで、**どこに高気圧が
あるか**は教えない。検出は教える。同じ「位置情報」でも中身が違ったことに
なる。この違いは、上の弱い証拠のなかでは最も筋の通った説明である。

## 二つ玉低気圧が下がった(-0.340)。計画の予測は実測で否定された

計画は狙い目としてこう書いていた。

> 二つ玉低気圧が狙い目。…定義が文字通り「低気圧が2つ」なので、検出器には
> 数えるだけの問題になる。早い段階で分かりやすい成果が出る可能性が高い。

`scripts/feature_report.py --label futatsudama_low` で全特徴量を測ると、
**数は手がかりになっていない。**

| 特徴量 | AUC | |
|---|---|---|
| `low_in_futatsudama_low` | 0.705 | 領域の在否 |
| `low_in_japan_sea_low` | 0.693 | |
| `low_cy` | 0.693 | 低気圧の南北位置 |
| `low_in_nankigan_low` | 0.605 | |
| **`n_low`** | **0.622** | 計画が「数えるだけ」と言った特徴量 |
| **`low_spread`** | **0.432** | 二つ玉のために入れたが**逆向き**だった |

`low_spread`(最も離れた2つの距離)は、こちらが二つ玉を狙って足したもので
ある。0.432 は逆向きの弱い関係で、**設計の意図と反対に働いていた。**
検出が1枚あたり4個前後の低気圧を出すので、散らばった誤検出があるほど
spread が大きくなり、本当の二つ玉とは関係が薄い。

**定義は数ではなく配置である。**`src/labels.py` の規約がそう書いていた。

> `futatsudama_low`(二つ玉低気圧)は、`japan_sea_low` と `nankigan_low` を
> 「置き換える」。個別の低気圧ラベルは付けない。

つまり「日本海側に1つ**かつ**南岸に1つ」。領域ごとの在否は別々の特徴量に
していたが、**その組を表す特徴量が無かった。**`low_in_japan_sea_and_nankigan`
を足した(2026-08-27)。木は組を作るのに深さを使うので、定義そのものが組で
あるなら最初から渡したほうがよい。

あわせて `west_high_east_low`(高気圧と低気圧の東西の差)も足した。西高東低は
ラベル名がそのまま配置を表しており、`high_cx` が0.260と効いていた。

## 台風が下がった(-0.702)

**予想どおり。**台風には H/L の文字が無い。中心は丸で囲んだ×で、名前は
`STS 2405 MARIA` という別フォントである
(`docs/2026-08-26-detection-prescreen.md`)。今の特徴量には台風の手がかりが
ほとんど無いので、0.177 は「信号が無い」ことの表れであって、方式の限界では
ない。**中心の印を入れれば変わる見込みが高い。**

## 停滞前線が下がった(-0.270)のは意外

下見では、停滞前線ラベルを停滞pxだけで **AUC 0.923** で分けられていた。
それが 0.516 に留まっている。AUCは順位だけを見る目安で、しきい値も
交差検証も通していない数字だったので、そのまま成績にはならない。
ただし0.923と0.516の開きは大きく、**下見のAUCを成績の予測に使えないことの
実例**として記録しておく。

---

## 検証データの季節が偏っていた(-0.157相当)

しきい値は検証データで決めるが、既定の `val_mode="tail"` は直近をまとめて
取るので季節が偏る。実測では**検証データに1〜4月と11〜12月しか入らず**、
梅雨・秋雨の停滞前線と夏の太平洋高気圧のしきい値が、その季節を見ずに
決まっていた。

`--val-mode spread` で通年にすると:

| ラベル | tail | spread | 差 |
|---|---|---|---|
| **停滞前線** | 0.516 | **0.673** | **+0.157** |
| 台風 | 0.177 | 0.291 | +0.114 |
| 西高東低 | 0.480 | 0.504 | +0.024 |
| 日本海低気圧 | 0.386 | 0.414 | +0.028 |
| オホーツク海高気圧 | 0.499 | 0.453 | -0.046 |
| 南岸低気圧 | 0.328 | 0.271 | -0.057 |
| **太平洋高気圧型** | 0.293 | **0.195** | **-0.098** |
| 全体 | 0.404 | 0.417 | +0.013 |

停滞前線は `stationary_px` のAUCが0.874あったのにF1が0.516だった。
**信号が無いのではなくしきい値が見当違いだった**ことが、これで確かめられた。

ただし全体では+0.013に留まり、陽性の少ないラベルは落ちている。spread は
検証週の前後も学習から除くので**学習データが減る**ためと思われる。
既定は tail のままにしてある。`cv_baseline` も tail で回っているので、
既定を変えると比較の条件が黙って変わる。**spread で比べるならCNN側も
spread で回し直すこと。**

## 訂正: +0.200 は precision を主張しすぎている

条件を変えて3回回したところ、オホーツク海高気圧は毎回違う値を出した。

| 実行 | オホーツク海 | CNNとの差 |
|---|---|---|
| `cv_features` (tail・38個) | 0.499 | +0.200 |
| `cv_features_spread` (spread・38個) | 0.453 | +0.154 |
| `cv_features2` (tail・40個) | 0.421 | +0.122 |

**3回とも CNN の 0.299 を上回っているので、勝ちは本物と見てよい。**
ただし差は **+0.122 〜 +0.200** の幅があり、「+0.200」と一つの数字で
言うのは precision を主張しすぎだった。

foldごとの標準偏差も大きい(`cv_features2` のオホーツク海は
0.49 / 0.49 / 0.28 で ±0.123)。**2432件に対して40個の特徴量は、木にとって
不安定な条件である。**

## 特徴量を2つ足しても改善しなかった

`low_in_japan_sea_and_nankigan` と `west_high_east_low` を足して回した
(`cv_features2`)。

| | 38個 | 40個 | foldの標準偏差 |
|---|---|---|---|
| 全体 | 0.404 | 0.408 | ±0.023 |
| 二つ玉低気圧 | 0.191 | 0.237 | **±0.101** |
| 停滞前線 | 0.516 | 0.619 | ±0.027 |
| オホーツク海 | 0.499 | 0.421 | ±0.123 |

二つ玉の +0.046 は fold間のばらつき(±0.101)に埋もれている。**そして
こちらが手を入れていない停滞前線が +0.103、オホーツク海が -0.078 動いて
いる。**これは特徴量の効果ではなく、木の当てはめの揺れである。

全体の macro F1 も、3つの条件で 0.404 / 0.417 / 0.408。幅0.013は foldの
標準偏差(0.004〜0.023)と同程度で、**条件の違いを区別できていない。**

### 訂正: 「木の当てはめの揺れ」ではなかった

上で差を「木の当てはめの揺れ」と書いたが、**これは誤りだった。**
seed を1・2・3と変えて回したところ、**3回とも小数点以下まで完全に同じ結果**
になった。`HistGradientBoostingClassifier` は既定で部分抽出をしないので、
同じデータからは必ず同じ木ができる(binningの部分抽出は n>10000 のときだけ、
early stopping も n<10000 では既定で無効)。

つまり 38個 → 40個 で オホーツク海が 0.499 → 0.421 と動いたのは、
**乱数ではなく特徴量を2つ足したことの決定的な結果**である。無関係な特徴量を
2つ足しただけで1つのラベルが 0.078 落ちる、ということ自体が
**2432件に対して40個の特徴量では入力の変化に敏感すぎる**ことを示している。

### ばらつきは seed ではなく学習データで測る

seed を振っても何も動かないので、`--bootstrap N` を足した。学習データを
重複ありで取り直して N 回当てはめ、成績の幅を出す。**特徴量を1つ2つ足した
ときの差が、この幅より小さいなら読めない。**

    python -m scripts.cv_features --features data\features.csv `
        --years 2023 2024 2025 --bootstrap 10 --out runs\cv_features_bs

foldごとの標準偏差(すでに出している)も、同じ目的で使える。実測では
オホーツク海が ±0.123、二つ玉低気圧が ±0.101 と大きい。

## ばらつきを測った結果、追いかけていた差は読めていなかった

`--bootstrap 10`(学習データを重複ありで取り直して10回)で測った。

| fold | macro F1 | 取り直した10回の幅 | 標準偏差 |
|---|---|---|---|
| 2023 | 0.403 | 0.377〜0.409 | 0.012 |
| 2024 | 0.433 | 0.407〜0.442 | 0.011 |
| 2025 | 0.387 | 0.357〜0.400 | 0.011 |

**学習データを取り直すだけで ±0.011 動く。**この物差しで、これまでの
比較を読み直すと:

| 比較 | 差 | 判定 |
|---|---|---|
| 38個 → 40個(特徴量を2つ追加) | +0.004 | **ばらつきの半分以下。読めない** |
| tail → spread | +0.013 | 約1σ。微妙 |
| **CNN との差** | **-0.234** | **約20σ。疑いなく本物** |

**こちらが足した特徴量は、どれも読める差を出していなかった。**
`low_in_japan_sea_and_nankigan` も `west_high_east_low` も、二つ玉低気圧の
定義や西高東低の名前から筋は通っているが、**この規模では効果を確認できない。**

ラベル別のばらつきも出すようにした(`--bootstrap` を付けると
「取り直しの幅」の列が出る)。**ラベルごとの勝ち負けは、macroの幅ではなく
その列と見比べて読むこと。**

## 次にやること

**特徴量の小さな追加はもう効かない。**ばらつきより大きい変更を入れる。

1. **中心の印(×・丸で囲んだ×)を入れる。**台風は最良の特徴量が
   `cold_length` 0.331 で、しかも前線の特徴量である。**台風固有の手がかりが
   皆無**なので、印を入れるまで上がらない。低気圧の誤検出も減る見込みが
   あり、二つ玉の頭打ちの原因もそこにある。`build_features --marks` で渡せる
2. **等圧線の向きと密度を足す。**計画が西高東低の判定に挙げていたが、今の
   検出には入っていない。西高東低は -0.300 で影響が大きい
3. **比べる前にばらつきを測る。**同じ条件を seed を変えて3回回す。
   1回1分なので、0.0x の差を追う前に必ずやること

## 手元だけで進められること(Claude抜きの手順)

判断基準まで書いてあるので、この節だけで進められる。

### 1. 中心の印を入れる(一番効く見込み・作業30分)

台風は最良の特徴量が `cold_length` 0.331 で、しかも前線の特徴量である。
**台風固有の手がかりが皆無**なので、印を入れるまで上がらない
(現在 0.196、CNNは0.879)。

手順:

1. 天気図を画像編集ソフトで開き、**ただの×**(高気圧の中心)と
   **丸で囲んだ×**(低気圧・台風の中心)を切り出す。H/L と同じ要領で、
   周りの等圧線は消す。3〜5個体ずつあるとよい
2. `data\marks\` に `cross.png` `cross2.png` … `circled.png` `circled2.png` … と置く
   (末尾の数字は自動でまとめて数える。白地に黒でも自動で反転する)
3. 走らせる:

```powershell
python -m scripts.build_features --in-dir $processed_dir `
    --templates data\templates --marks data\marks `
    --out data\features_marks.csv --workers 8
python -m scripts.cv_features --features data\features_marks.csv `
    --years 2023 2024 2025 --bootstrap 10 --out runs\cv_marks
python -m scripts.compare_runs runs\cv_baseline runs\cv_features_bs runs\cv_marks
```

**判断**: 台風の F1 が現在の 0.196 から、ばらつき(±0.067)の2倍
つまり **0.33 以上**になれば効いている。ならなければ、印だけでは台風は
取れないということなので、名前の文字(`STS 2405 MARIA`)を狙うことになる。

印が入ると位置の主役が×に変わるので(`build_features` の `--marks`)、
低気圧の誤検出が減って二つ玉低気圧(現在 0.237、±0.080)も動く見込みがある。
**0.40 以上**なら効いている。

### 中心の印を渡すときの名前(実際に躓いた点)

`symbol_of` は名前の末尾の数字と `_` 以降を落とす。したがって:

    cross / cross2 / cross_b       -> cross   (高気圧)
    circle_cross / circled / circle2 -> circle… (低気圧・台風)

**丸で囲んだ×は `circle` で始まる名前にすること。**当初 `MARK_LOW` を
`"circled"` と決め打ちしていたため、実際に使われた `circle_cross` が
低気圧として数えられていなかった。前方一致に直した。

**印は `--marks` に渡すこと。**`--templates` に置くと H と L しか見ないので
黙って無視される。入っていたら指摘するようにした。

**テンプレートに前線を含めないこと。**手で切り出した画像は濃淡で2値化する
ので、赤い前線(グレースケール78)も青い前線(同32)もインクとして入る。
一方、天気図側は**黒の帯だけ**で照合するので前線は存在しない。テンプレートに
だけ余分なインクがある状態になり、一致スコアが下がる。

印は小さく丸い塊で、閉じた等圧線の内側にあって線と重なりにくい。**H/L と
違って `cut --box` がそのまま使える**(黒の帯で切り出すので前線は自動的に
除かれる)。手で消すより確実である。

## この結果の読み方

**「CNNのほうが良いので物体検出は筋が悪い」と読んではいけない。**

比べているのは、CNNが2432枚を丸ごと学習した結果と、**38個の手作りの
特徴量**である。特徴量には等圧線の情報が一切入っておらず、台風の手がかりも
