2026-08-27

`docs/2026-08-26-detection-plan.md` の Phase 3・4 を一度通した結果。
天気図から記号と前線を検出し、40個の特徴量に変え、木のモデルで10ラベルを
分類した。同じfold・同じラベル・同じ評価コードで既存CNNと比べている。

**全体では負けた。ただし計画の中心にある仮説は支持された。**

## オホーツク海高気圧(+0.122、2.0σ)。示唆的だが確定ではない

**これが計画の主題だった。**計画は次のように書いていた。

> オホーツク海高気圧は、記録が本当にオホーツク海高気圧の58枚に対してすら
> lift 1.24・peak的中率 8.6%。**正解のときですらオホーツク海を見ていない。**
> 物体検出で中心座標を明示的に取れば、位置は構造的に手に入る。

10ラベルのうち**唯一、特徴量がCNNを上回った。**しかもCNNが最も苦手として
いたラベルである。手がかりは `high_in_okhotsk_high`(AUC 0.883)で、全ラベル
全特徴量のなかで最も強い単独の信号だった。

**ただし確定と言うには足りない。**

- 差 +0.122 に対し、学習データを取り直したときの幅が ±0.053〜0.061。**2.0〜2.3σ**
- foldごとに 0.49 / 0.49 / **0.28** と割れており、**2025年のfoldは
  CNNの平均(0.299)を下回っている**
- 条件を変えた3回の実行で 0.499 / 0.453 / 0.421 と動く(差 +0.200 〜 +0.122)

**「位置を明示的に与えるとオホーツク海高気圧が良くなる」という方向は
支持されたが、大きさは確定していない。**再現するなら、この1ラベルに絞って
検出の精度を上げ、foldを増やして測り直すこと。

計画は「位置情報の欠如」という説明をCoordConvで試して否定していた
(F1 0.326→0.270)。CoordConvは座標を入力に足すだけで、**どこに高気圧が
あるか**は教えない。検出は教える。同じ「位置情報」でも中身が違ったことに
なる。この違いは、上の弱い証拠のなかでは最も筋の通った説明である。

## 検証データの季節が偏っていた(-0.157相当)

しきい値は検証データで決めるが、既定の `val_mode="tail"` は直近をまとめて
取るので季節が偏る。実測では**検証データに1〜4月と11〜12月しか入らず**、
梅雨・秋雨の停滞前線と夏の太平洋高気圧のしきい値が、その季節を見ずに
決まっていた。

`--val-mode spread` で通年にすると:

| ラベル | tail | spread | 差 |
|---|---|---|---|
| **停滞前線** | 0.516 | **0.673** | **+0.157** |
| 台風 | 0.177 | 0.291 | +0.114 |
| 西高東低 | 0.480 | 0.504 | +0.024 |
| 日本海低気圧 | 0.386 | 0.414 | +0.028 |
| オホーツク海高気圧 | 0.499 | 0.453 | -0.046 |
| 南岸低気圧 | 0.328 | 0.271 | -0.057 |
| **太平洋高気圧型** | 0.293 | **0.195** | **-0.098** |
| 全体 | 0.404 | 0.417 | +0.013 |

停滞前線は `stationary_px` のAUCが0.874あったのにF1が0.516だった。
**信号が無いのではなくしきい値が見当違いだった**ことが、これで確かめられた。

ただし全体では+0.013に留まり、陽性の少ないラベルは落ちている。spread は
検証週の前後も学習から除くので**学習データが減る**ためと思われる。
既定は tail のままにしてある。`cv_baseline` も tail で回っているので、
既定を変えると比較の条件が黙って変わる。**spread で比べるならCNN側も
spread で回し直すこと。**

## 訂正: +0.200 は precision を主張しすぎている

条件を変えて3回回したところ、オホーツク海高気圧は毎回違う値を出した。

| 実行 | オホーツク海 | CNNとの差 |
|---|---|---|
| `cv_features` (tail・38個) | 0.499 | +0.200 |
| `cv_features_spread` (spread・38個) | 0.453 | +0.154 |
| `cv_features2` (tail・40個) | 0.421 | +0.122 |

**3回とも CNN の 0.299 を上回っているので、勝ちは本物と見てよい。**
ただし差は **+0.122 〜 +0.200** の幅があり、「+0.200」と一つの数字で
言うのは precision を主張しすぎだった。

foldごとの標準偏差も大きい(`cv_features2` のオホーツク海は
0.49 / 0.49 / 0.28 で ±0.123)。**2432件に対して40個の特徴量は、木にとって
不安定な条件である。**

## 特徴量を2つ足しても改善しなかった

`low_in_japan_sea_and_nankigan` と `west_high_east_low` を足して回した
(`cv_features2`)。

| | 38個 | 40個 | foldの標準偏差 |
|---|---|---|---|
| 全体 | 0.404 | 0.408 | ±0.023 |
| 二つ玉低気圧 | 0.191 | 0.237 | **±0.101** |
| 停滞前線 | 0.516 | 0.619 | ±0.027 |
| オホーツク海 | 0.499 | 0.421 | ±0.123 |

二つ玉の +0.046 は fold間のばらつき(±0.101)に埋もれている。**そして
こちらが手を入れていない停滞前線が +0.103、オホーツク海が -0.078 動いて
いる。**これは特徴量の効果ではなく、木の当てはめの揺れである。

全体の macro F1 も、3つの条件で 0.404 / 0.417 / 0.408。幅0.013は foldの
標準偏差(0.004〜0.023)と同程度で、**条件の違いを区別できていない。**

### 訂正: 「木の当てはめの揺れ」ではなかった

上で差を「木の当てはめの揺れ」と書いたが、**これは誤りだった。**
seed を1・2・3と変えて回したところ、**3回とも小数点以下まで完全に同じ結果**
になった。`HistGradientBoostingClassifier` は既定で部分抽出をしないので、
同じデータからは必ず同じ木ができる(binningの部分抽出は n>10000 のときだけ、
early stopping も n<10000 では既定で無効)。

つまり 38個 → 40個 で オホーツク海が 0.499 → 0.421 と動いたのは、
**乱数ではなく特徴量を2つ足したことの決定的な結果**である。無関係な特徴量を
2つ足しただけで1つのラベルが 0.078 落ちる、ということ自体が
**2432件に対して40個の特徴量では入力の変化に敏感すぎる**ことを示している。

### ばらつきは seed ではなく学習データで測る

seed を振っても何も動かないので、`--bootstrap N` を足した。学習データを
重複ありで取り直して N 回当てはめ、成績の幅を出す。**特徴量を1つ2つ足した
ときの差が、この幅より小さいなら読めない。**

    python -m scripts.cv_features --features data\features.csv `
        --years 2023 2024 2025 --bootstrap 10 --out runs\cv_features_bs

foldごとの標準偏差(すでに出している)も、同じ目的で使える。実測では
オホーツク海が ±0.123、二つ玉低気圧が ±0.101 と大きい。

## ばらつきを測った結果、追いかけていた差は読めていなかった

`--bootstrap 10`(学習データを重複ありで取り直して10回)で測った。

| fold | macro F1 | 取り直した10回の幅 | 標準偏差 |
|---|---|---|---|
| 2023 | 0.403 | 0.377〜0.409 | 0.012 |
| 2024 | 0.433 | 0.407〜0.442 | 0.011 |
| 2025 | 0.387 | 0.357〜0.400 | 0.011 |

**学習データを取り直すだけで ±0.011 動く。**この物差しで、これまでの
比較を読み直すと:

| 比較 | 差 | 判定 |
|---|---|---|
| 38個 → 40個(特徴量を2つ追加) | +0.004 | **ばらつきの半分以下。読めない** |
| tail → spread | +0.013 | 約1σ。微妙 |
| **CNN との差** | **-0.234** | **約20σ。疑いなく本物** |

**こちらが足した特徴量は、どれも読める差を出していなかった。**
`low_in_japan_sea_and_nankigan` も `west_high_east_low` も、二つ玉低気圧の

ラベル別のばらつきも出すようにした(`--bootstrap` を付けると
「取り直しの幅」の列が出る)。**ラベルごとの勝ち負けは、macroの幅ではなく

## 次にやること

**特徴量の小さな追加はもう効かない。**ばらつきより大きい変更を入れる。

1. **中心の印(×・丸で囲んだ×)を入れる。**台風は最良の特徴量が
   `cold_length` 0.331 で、しかも前線の特徴量である。**台風固有の手がかりが
   皆無**なので、印を入れるまで上がらない。低気圧の誤検出も減る見込みが
   あり、二つ玉の頭打ちの原因もそこにある。`build_features --marks` で渡せる
2. **等圧線の向きと密度を足す。**計画が西高東低の判定に挙げていたが、今の
   検出には入っていない。西高東低は -0.300 で影響が大きい
3. **比べる前にばらつきを測る。**同じ条件を seed を変えて3回回す。
   1回1分なので、0.0x の差を追う前に必ずやること

## 手元だけで進められること(Claude抜きの手順)

判断基準まで書いてあるので、この節だけで進められる。

### 1. 中心の印を入れる ― 【済・不採用】

**やった。採らなかった。**判定は上の「判定: 中心の印は採用しない」を読むこと。
以下は当時の見立てで、**結果は外れた**(台風は 0.196 -> 0.145 と悪化した)。
手順そのものは動くので、別の目的で印を使いたくなったときの参考に残す。

台風は最良の特徴量が `cold_length` 0.331 で、しかも前線の特徴量である。
**台風固有の手がかりが皆無**なので、印を入れるまで上がらない
(現在 0.196、CNNは0.879)。

手順:

1. 天気図を画像編集ソフトで開き、**ただの×**(高気圧の中心)と
   **丸で囲んだ×**(低気圧・台風の中心)を切り出す。H/L と同じ要領で、
   周りの等圧線は消す。3〜5個体ずつあるとよい
2. `data\marks\` に `cross.png` `cross2.png` … `circled.png` `circled2.png` … と置く
   (末尾の数字は自動でまとめて数える。白地に黒でも自動で反転する)
3. **まず20枚で当たり具合を見る**(全部走らせる前に。1〜2分):

```powershell
python -m scripts.build_features --in-dir $processed_dir `
    --templates data\templates --marks data\marks `
    --out data\check_marks.csv --limit 20 --workers 4
```

最後に1枚あたりの検出数と、印から一番近い文字までの距離の分布が出る。
見るところ:

* **`marks`** ― 拾えた印の数。天気図1枚の中心はふつう5〜10個
* **`orphan_marks`** ― 文字と組にならなかった印。3割を超えると警告が出る。
  `--mark-radius` が狭すぎるか、文字を取りこぼしている
* **`high` と `low` の比** ― どちらかに極端に寄っていたら種別付けが壊れている
* **距離の分布** ― `--mark-radius` はこの実測から決める。「9割」の値より
  少し広く取ればよい

当たっていれば `data\check_marks.csv` を消して本番へ。

4. 走らせる:

```powershell
python -m scripts.build_features --in-dir $processed_dir `
    --templates data\templates --marks data\marks `
    --out data\features_marks.csv --workers 8
python -m scripts.cv_features --features data\features_marks.csv `
    --years 2023 2024 2025 --bootstrap 10 --out runs\cv_marks
python -m scripts.compare_runs runs\cv_baseline runs\cv_features_bs runs\cv_marks
```

**判断**: 台風の F1 が現在の 0.196 から、ばらつき(±0.067)の2倍
つまり **0.33 以上**になれば効いている。ならなければ、印だけでは台風は
取れないということなので、名前の文字(`STS 2405 MARIA`)を狙うことになる。

印が入ると位置の主役が×に変わるので(`build_features` の `--marks`)、
低気圧の誤検出が減って二つ玉低気圧(現在 0.237、±0.080)も動く見込みがある。
**0.40 以上**なら効いている。

### 中心の印の使い方(実際に躓いた点)

**印の形では高低を見分けられない。**これが一番大きな躓きだった。

丸で囲んだ×(低気圧)を `circle_cross` テンプレートで拾おうとすると失敗する。
図の側の丸は大きさも太さもまちまちなので、丸ごと当てるテンプレートは
しきい値を割る。一方、丸の内側の×はいつでも完璧に当たる。実測:

    図の丸 r=28 太さ=4 -> circle_cross=1.00   (テンプレートと同じ大きさ)
    図の丸 r=24 太さ=3 -> cross=0.94
    図の丸 r=33 太さ=5 -> cross=1.00
    図の丸 r=22 太さ=6 -> cross=0.79

しかも重なった検出はスコアの高いほうだけを残すので、**低気圧が
すべて高気圧として数えられる**。実際の20枚で 高7.70 / 低0.20 だった
(天気図1枚の中心はふつう高低あわせて5〜10個なので、総数は合っているのに
種別が全部片側に寄っていた)。

そこで役割を分けた。**位置は印から、種別はいちばん近い H/L の文字から取る。**
×は中心そのものなので位置として正しく、文字は形が安定していて種別として
正しい。テンプレートの名前は自由でよくなった。

### 二つの検出は互いを裏書きする

役割を分けたあと、20枚で 印7.90 / 種別が付いたもの3.10 / 余り4.80 になった。
重ね描きで見ると、余りの中身は2種類だった:

* **本物の低気圧の中心**(998hPa と 996hPa)。L の文字が等圧線に横切られて
  しきい値 0.65 を割り、拾えていなかった
* **誤検出**。数字の「4」や「6」の交差、L のラベルと等圧線の交差

この2つは同じ手当てで両方直る。文字を `--letter-threshold`(既定0.50)まで
緩めて拾い、**しきい値を割った文字は印と組になったものだけを採る**。

* 等圧線に隠れた L は、そこに×があるという裏書きで取り戻せる
* ×の誤検出は、近くに文字が無いので種別が付かず、特徴量に入らない
* 緩めたせいで増える偽の文字は、×が無いので捨てられる

**印と文字は別の形なので、同じ場所に偶然そろって誤検出することはまれ**
である。これが裏書きが成り立つ理由で、印にも文字にも同じテンプレートを
使うと成り立たない(テストではそこを分けてある)。

20枚での効き目:

| | 裏書き前 | 裏書き後 |
|---|---|---|
| 低気圧 | 0.90 | **3.00** |
| 高気圧 | 2.20 | 2.65 |
| 余った印 | 4.80 | 2.25 |
| 裏書きで採れた文字 | ― | 2.05 |

(裏書き後はしきい値0.42・半径0.10。印は1枚あたり7.90で変わらない。)

### 緩め方は掃引して決めた

20枚で `--letter-threshold` を振った:

| しきい値 | 拾えた L | 組になった低気圧 | 余った印 |
|---|---|---|---|
| 0.50 | 3.90 | 2.75 | 2.50 |
| **0.42** | **4.20** | **3.00** | **2.25** |
| 0.35 | 6.00 | 3.00 | 2.25 |

0.35 は文字を1.8枚多く拾うが、**組になった数はまったく増えない**(低気圧も
余った印も0.42と完全に同一)。増えた分はすべて印の裏書きが無い偽の文字で、
捨てられている。0.42 が本物を拾いきり、偽を拾い始める直前の点。

**「拾えた文字が増えた」は成果ではない。**組になった数が増えたかどうかで
判断すること。ここを取り違えると、偽の文字を増やしただけで満足してしまう。

### 判定: 中心の印は採用しない(2026-08-28)

位置を捨てるバグを直したあとの本番(2432枚):

| | 印なし | 印あり | 差 |
|---|---|---|---|
| macro F1 | 0.408 ± 0.023 | 0.411 ± 0.012 | **+0.003(読めない)** |
| 台風 | 0.196 | **0.145** | -0.051 |
| 二つ玉低気圧 | 0.237 | 0.309 | +0.072(±0.100、読めない) |
| 日本海低気圧 | 0.391 | 0.480 | +0.089(2.6σ) |
| 移動性高気圧 | 0.657 | 0.705 | +0.048(2.0σ) |
| 停滞前線 | 0.619 | 0.650 | +0.031(1.9σ) |
| **オホーツク海高気圧** | **0.421** | **0.324** | **-0.097(1.9σ)** |

**事前に決めた線(台風0.33以上・二つ玉0.40以上・macroが同等なら不採用)を
どれも満たさない。** 印を入れた目的は台風だったが、その台風が唯一はっきり
悪化した。

決め手はオホーツク海高気圧である。**これは特徴量方式が唯一CNN(0.299)を
上回っていたラベルで、この方式の存在意義そのものだった。**印を入れると
0.324 まで落ちて優位がほぼ消える。

ばらつきは大きく減った(fold間 0.023 -> 0.005、取り直し ±0.023 -> ±0.012)。
安定性は本物の改善だが、平均が動かず、要のラベルが落ちるので採らない。

#### なぜ悪化したかの見立て(未検証)

**位置の列の意味が行ごとに混ざっている。**印と組めた系は×(真の中心)の
位置、組めなかった系は H/L 文字の位置になる。文字は中心から相対座標で
0.074 ほどずれた場所にある(実測の距離の中央値がまさにこの値)。

オホーツク海高気圧は「オホーツク海の矩形の中にあるか」が定義そのもので、
7%のずれが混在すると内外判定が揺れる。台風も位置が効くラベルである。

**印は位置を正確にしたが、正確なものと不正確なものを同じ列に混ぜた。**
全部を印に揃えるには組めなかった系を捨てるしかなく、それは -0.068 の
バグに戻る。この二律背反が解けない限り、印は入れないほうがよい。

試すなら、位置が印由来か文字由来かを示す列を足して木に補正させる、あるいは
文字の位置を「文字の向きから推定した中心」に直す、といった道がある。
**ただしどちらも、方式全体がCNN(0.641)に0.23届いていないという事実を
変えない。**

#### 検出そのものは下見どおりだった

2432枚での検出数は20枚の下見とよく合っていた(印 7.52 対 7.90、低気圧
3.40 対 3.00、余り 1.95 対 2.25)。**下見の20枚は代表的だった。**
検出を良くする作業は成功していて、それでも分類が良くならなかった、という
のがこの節の結論である。

### 印は位置を減らしてはいけない(実測で -0.068)

2432枚で走らせた最初の結果は**悪化**だった:

| | 印なし | 印あり | 差 |
|---|---|---|---|
| macro F1 | 0.408 | **0.340** | **-0.068**(3foldとも同符号、約3σ) |
| 停滞前線 | 0.619 | 0.473 | -0.146 |
| オホーツク海高気圧 | 0.421 | 0.187 | -0.234 |
| 台風 | 0.196 | 0.296 | +0.100(線の0.33に届かず) |

**停滞前線は色マスクから作っていて印とは無関係**なのに落ちた。ここが原因を
指していた。印を入れたとき、組にならなかった文字を(縁のもの以外)捨てて
いた。印なしでは文字の位置がそのまま高低気圧の位置になっていたので、
**印は位置を良くするはずが位置の総数を減らしていた**。しかも減り方が画像
ごとに違うので、同じ列の意味が行によって変わる。位置の特徴量は全ラベルの木
に入るので、無関係なラベルまで巻き添えになる。

直し方は「組になったものは印の位置、組にならなかった強い文字は文字の位置」。
これなら印なしの情報を一切失わない。

**教訓**: 検出を良くする改造は、良くなった数だけでなく**前より減っていない
こと**を確かめること。下見の20枚では検出数しか見ておらず、位置が捨てられて
いることに気づけなかった。

### 4通り試して分かったこと: 詰まっていたのは「位置」ではなく「検出」

位置情報の注入点を4通り試した。**すべて `val_mode=tail` で条件を揃えてある。**

| 注入点 | macro F1 | 基準比 | foldごとの差 | 判定 |
|---|---|---|---|---|
| 基準(素の天気図) | 0.647 | ― | ― | ― |
| ① 座標を入力チャンネルに(CoordConv) | ― | ― | ― | 効かず(別実験) |
| ② 学習の答えに加える(補助タスク) | 0.651 | +0.004 | +0.017/+0.007/-0.013 | **効かず** |
| **③ 画像に描き込む(枠)** | **0.667** | **+0.021** | +0.002/+0.047/+0.013 | **効いた** |
| ③+① 描き込み + 座標 | 0.669 | +0.022 | ③比 +0.035/-0.023/-0.008 | **③と差なし** |

#### 「検出できたうえで座標を渡せば効く」は否定された

「①が効かなかったのは高低気圧を検出できていなかったからで、検出が明示された
状態なら座標が効くはず」という仮説を立て、`runs/cv_annot_coord` で試した。
**枠だけ(0.667)と枠+座標(0.669)の差は +0.001 で、符号もばらつく。**

ラベル別に見ても、**fold間ばらつきの1.5倍を超えた差は1つも無い。**
狙いだったオホーツク海高気圧も 0.367 -> 0.376(0.2σ)で動かなかった。

なお `CoordConv` は検出とは無関係な仕組みで、x座標・y座標を正規化した2枚の
マップを画像に連結するだけである(`src/model.py`)。検出の成否にかかわらず
座標は常に全画素に与えられていた。

#### 説明を改める

当初この系の弱点を「**絶対位置を読めないこと**」と考えていた。しかし:

* 位置を**入力**として渡す(①)→ 効かない。検出が明示された状態でも効かない
* 位置を**出力**として答えさせる(②)→ 効かない
* 位置を**画像に描く**(③)→ 効く(+0.021、3foldとも正)

**位置を渡す2通りが効かず、絵として描くものだけが効いた。**これは「位置が
足りなかった」では説明できない。

**詰まっていたのは「どこにあるか」ではなく「そこに何かがあると気づくこと」
だったと考えるほうが、4つの結果すべてと整合する。**Grad-CAM で、オホーツク海
高気圧を正解している58枚でもオホーツク海を見ている割合が8.6%しかなかったのは、
「位置は分かるが読み違えた」のではなく「**そもそも高気圧を見つけていなかった**」
ということになる。見つけられていないものに座標を与えても使いようがない。

伸びたのが移動性高気圧(+0.068、4.3σ)とオホーツク海高気圧(+0.097、2.2σ)
という**どちらも高気圧のラベル**だったことも、これで筋が通る。H の文字は
1枚あたり2.80しか拾えず、L の3.90〜4.20より少なかった(下見の実測)。
**見つけにくかったほうが、枠を描いた恩恵を大きく受けた。**

(これは4つの結果を後から説明する筋書きであって、直接確かめたわけではない。
確かめるなら、枠を描いた画像で Grad-CAM を取り直し、注視割合が8.6%から
上がっているかを見るのが素直である。)

**ほぼ同一(+0.001)。前線の縁取りは全体に何も足していない。**
処理も減り、前線の検出誤りを入力に焼き付ける危険も減るので、
**枠だけのほうが素直である。**

ただしラベル別に見ると入れ替わりがあり、多くは fold間のばらつきの範囲:

#### 確かめること

* **まず分割条件をそろえる**(上の注意)。それが済むまで上積みの値は暫定
* **2023年だけ下がった理由。**両方の変種で2023年が負である。ただし
  `cv_baseline` の2023年(0.654)はそれ自体が baseline の最良foldなので、
  「描き込みが悪い」のではなく「基準が良い」だけの可能性もある
* 描き込んだ画像と特徴量モデルの**混合**(まだ試していない)

### ③の結果を画像に描き込んで①に渡す(実装の説明)

`scripts/annotate_charts.py`。検出した高低気圧に枠を、前線に縁取りを描いた
画像を作り、それを `--data-dir` にして学習する。**学習側のコード変更は要らない。**

    天気図 -> 検出(STEP1・STEP2) -> 描き込み -> 注釈付き画像 -> CNN

これは3つめの注入点である。1つめ(座標を入力チャンネルに足す=CoordConv)は
効かず、2つめ(検出結果を学習の答えに加える)は +0.009 にとどまった。

**この方式のもう一つの利点は、成績とは別のところにある。**Grad-CAM は
「モデルがどこを見たか」しか示さないが、注釈付き画像は「**検出が正しかったか**」
を示す。運用でAIの判定を人が検証する場面では、こちらのほうが直接的である。
成績が動かなくても、この可視化だけで価値がありうる。

#### 期待しすぎないための但し書き

**枠を描いても、CNNが位置を絶対座標で読めるようにはならない。**畳み込みは
平行移動に対して同等の応答を返すので、「枠がオホーツク海にある」ことは依然
として読み取りにくい。効くとすれば「**見つけやすくなる**」ほうであって、
「どこにあるか分かる」ほうではない。したがって**オホーツク海高気圧は
動かない見込み**で、動くとすれば前線に関わるラベルのほうだと予想する。

H/L の文字も前線も元の天気図に既に描かれている。これは情報の追加ではなく
**強調**である。

**検出の誤りが入力そのものに焼き付く。**補助の答えとして渡す場合は損失に
混じるだけだが、描き込むとモデルはそれを本物として扱う。1枚あたり約2.25個の
誤検出が残っているので、その分は嘘を教えることになる。

#### 実装で気をつけたこと

* **前線そのものは塗り替えず、周りに縁取りだけを描く。**塗り替えると天気図が
  元から持っている赤(温暖)・青(寒冷)の区別が消える。強調のつもりが情報の
  削除になる
* **全部の前線の元画素をまとめて守る。**自分のマスクだけ避けると、あとから
  描く縁取りが別の前線の元画素を塗った(実測で1割)
* **描き込みの色は、既存の色帯と重ならないものだけを使う。**当初 紫を低気圧の
  枠に使おうとしたが、閉塞前線の帯に入っていた。重なると人が見て区別できず、
  この画像に対して色マスクをもう一度かけることもできなくなる。空いているのは
  色相21〜99(橙〜黄〜緑〜シアン)だけである。`tests/test_annotate.py` が
  全色を機械的に確かめている
* 枠は輪郭だけ。塗りつぶすと下の天気図が消える


#### 最初の実行で検出が漏れた(2026-08-30)

実物で1枚あたり3個しか枠が付かなかった。下見(高2.65 / 低3.40)より明らかに
少ない。原因は2つあり、どちらも描き込み側の問題だった。

1. **`--marks` を渡していなかった。**`analyse_chart` の弱いしきい値は
   **印がある場合にだけ効く**設計(`weak = letter_threshold if marks else
   threshold`)なので、印なしでは等圧線に横切られた H/L が全部落ちる。
   998hPa・996hPa の低気圧がまさにこれだった。**必ず `--marks` を渡すこと。**
2. **縁にある文字を描いていなかった。**`split_by_edge` が highs/lows から
   外すのは「文字の位置は中心ではないので矩形の内外判定に使うと嘘になる」
   ためであって、そこに系が無いという意味ではない。描かないと拾えているのに
   拾えていないように見える(図の上端の H が2つ漏れた)。細線で描いて
   中心として信用できるものと見分けるようにした

```powershell
python -m scripts.annotate_charts --in-dir $processed_dir `
    --templates data\templates --marks data\marks `
    --out-dir data\annotated --workers 8
python -m scripts.cross_validate --data-dir data\annotated `
    --labels data\labels_v2.csv --years 2023 2024 2025 --out-dir runs\cv_annot
python -m scripts.compare_runs runs\cv_baseline runs\cv_annot
```

**本番の前に必ず数枚を目で見ること。**枠が本物の高低気圧に付いているか、
前線の縁取りが実際の前線と合っているかを確かめてから学習に回す。誤検出が
入力に焼き付く方式なので、検出の質がそのまま結果に効く。

### ③を①の教師にする(実装の説明)

混ぜるのは「答えを足し合わせる」やり方で、**①自身は変わらない**。CNNは
相変わらず H や L を数えていない。そこを直すために、検出から作った数値を
**学習の答えとして**加えられるようにした。

**なぜ入力ではなく出力なのか。**位置を入力として渡す CoordConv は既に試して
効かなかった(`docs/2026-08-25-attention-regions.md`)。全体は 0.641 -> 0.638、
オホーツク海高気圧はむしろ 0.33 -> 0.27。Grad-CAMで見ると、そのラベルを
正解している58枚でもオホーツク海を見ている割合は8.6%しかなく、座標を与えても
見る場所は変わらなかった。**入力は無視できるが、答えさせられる項目は無視
できない。**

仕組み(`src/model.py` の `AuxiliaryTargets`):

* 中のネットの出力を `10 + 補助の本数` にし、前半を10ラベル、後半を補助として
  切り分ける。最後の全結合の手前まで特徴を共有するので、補助を当てるために
  作られた表現が10ラベル側にも効く
* **`model(x)` は10ラベルぶんしか返さない。**推論・評価・Grad-CAM・混合など
  既存の経路は無改造で動く。学習だけが `forward_with_aux` を呼ぶ
* 欠測は NaN のまま渡し、損失で飛ばす(`src/train.py` の `masked_mse`)。
  0で埋めると「図の左上に高気圧がある」と教えることになる
* 補助の答えが無い行は**捨てない**。捨てると画像が減って10ラベルの学習まで痩せる
* 標準化の統計は**学習データの行だけ**から求める(`compute_aux_stats`)
* **モデル選択の指標は10ラベル側のまま**。補助を当てるのは目的ではなく手段
  なので、補助まで含めた損失で選ぶと目的からずれる

```powershell
python -m scripts.cross_validate --data-dir $processed_dir `
    --labels data\labels_v2.csv --years 2023 2024 2025 `
    --aux-features data\features.csv --aux-weight 0.3 --out-dir runs\cv_aux03
python -m scripts.compare_runs runs\cv_baseline runs\cv_aux03
```

**重みは振って決めること。**0.1 / 0.3 / 1.0 の3通りを回し、`cv_baseline`
(0.641、foldごとのばらつき0.013)と比べる。**判断は macro F1 と
オホーツク海高気圧の両方で見る。**位置を見させるのが狙いなので、全体が
動かなくてもオホーツク海高気圧が上がれば筋は通っている。逆に全体が下がる
なら重みが大きすぎる。

測った結果は上の節にある。**全体では +0.009 にとどまり、狙ったラベル
(オホーツク海高気圧)は動かなかった。**

#### なぜ混ぜる価値があったか

### 次の一手: 混ぜる(`scripts/ensemble_chart_features.py`)

特徴量方式が単独でCNNに勝てないことは確定したが、**誤り方が違う**なら
混ぜて上積みが取れる。前例がある(`docs/2026-08-21-chart-vs-era5-grid.md`):

天気図 + ERA5格子では全体 +0.010、**いちばん伸びたのは移動性高気圧
0.726 -> 0.748(+0.023)**だった。伸びたのは「両者とも中程度で、違う誤りを
しているラベル」で、得意分野が逆のラベルではなかった。

移動性高気圧はここでも条件が揃っている:

| | CNN | 特徴量 | 差 |
|---|---|---|---|
| 移動性高気圧 | 0.726 | 0.657〜0.705 | -0.02〜-0.07 |

**この近さが要点である。**特徴量側は `n_high` と `high_in_migratory_high`
を明示的に持っているので、高気圧が1つも無い天気図で移動性高気圧を出す
誤りは起こしにくい。CNNは H を数えていない(Grad-CAMで確認済み)。

再学習は不要。CNNの重みはfoldごとに保存済み、木は数秒で当てはめ直せる。
重みと閾値は検証データでラベルごとに決める(**一律の重みにすると得意分野が
逆のラベルどうしが妥協させられ、実測で天気図単独を下回った**)。

```powershell
python -m scripts.ensemble_chart_features --data-dir $processed_dir `
    --labels data\labels_v2.csv --features data\features.csv `
    --chart-weights runs\cv_baseline --years 2023 2024 2025 --out runs\cv_blend
python -m scripts.compare_runs runs\cv_baseline runs\cv_blend
```

**判断**: 全体で +0.013(foldごとのばらつき)を超え、3foldとも同符号なら
効いている。ラベル別では移動性高気圧とオホーツク海高気圧を見る。
「混ぜた割合」が0のラベルは、検証データが「混ぜないほうがよい」と判断した
ということで、そこは天気図のみと同じ結果になる。

### 半径は分布から決まった

印から一番近い文字までの距離(20枚):

    10%:0.056  30%:0.067  50%:0.074  70%:0.081  80%:0.095  90%:0.134  100%:0.308

8割までが 0.095 以内に固まり、そこから先へ飛ぶ。既定を 0.10 にした
(固まりの外縁)。広げすぎると、誤検出の印が**中心が枠外の系の文字を
横取りして偽の位置を作る**ので、届く割合を増やすこと自体は目的ではない。

**印は `--marks` に渡すこと。**`--templates` に置くと H と L しか見ないので
黙って無視される。入っていたら指摘するようにした。

**テンプレートに前線を含めないこと。**手で切り出した画像は濃淡で2値化する
ので、赤い前線(グレースケール78)も青い前線(同32)もインクとして入る。
一方、天気図側は**黒の帯だけ**で照合するので前線は存在しない。テンプレートに
だけ余分なインクがある状態になり、一致スコアが下がる。

印は小さく丸い塊で、閉じた等圧線の内側にあって線と重なりにくい。**H/L と
違って `cut --box` がそのまま使える**(黒の帯で切り出すので前線は自動的に
除かれる)。手で消すより確実である。

**印は文字より小さいので、縮小率を分ける。**実測で、H/L の文字は約95x117
だが中心の印は約31x31しかない。文字に効く `--scale 0.7` を印にも当てると
22x22になり、丸と×の細部が潰れる。`--mark-scale`(既定1.0=原寸)で分けた。

最初にこれを分けずに走らせたとき、2023年foldの macro F1 が印なしの
**0.403 から 0.321 に落ちた**。`analyse_chart` はその画像で印が1つでも
当たれば位置の主役を印に切り替えるので、**印が半端にしか当たらないと、
文字から得ていた位置の情報まで失う**。悪化はここが原因の可能性が高い。
だから本番の前に20枚で検出数を見ること(上の手順3)。

**全部NaNの列があると学習が落ちる。**`ValueError: window shape cannot be
larger than input array shape` が `bootstrap_spread` の中から出る。
HistGradientBoosting は欠測を扱えるが、1つも値が無い列だけは扱えない
(定数列は通る)。ブートストラップで学習データを取り直すと、希な特徴量が
たまたま全滅してここに落ちる。`drop_empty_columns` で落とすようにした。

## この結果の読み方

**「CNNのほうが良いので物体検出は筋が悪い」と読んではいけない。**

比べているのは、CNNが2432枚を丸ごと学習した結果と、**38個の手作りの
特徴量**である。特徴量には等圧線の情報が一切入っておらず、台風の手がかりも
無い。その状態で、CNNが最も苦手なラベルを +0.200 上回った。

計画の目的は「CNNのブラックボックス判定ではなく、予報官が何を見てどう
判断したかをAIに学習させること」だった。**オホーツク海高気圧の +0.200 は、
その方向に効くという最初の実測値である。**
